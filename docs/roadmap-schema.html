Roadmap — Data Model

Signal · database schema for the Roadmap section, derived from the prototype's in-memory model

1The big picture

Two axes joined by links — not one pyramid. Product structure describes what the product is made of; the work axis describes what we're doing and why. Weekly Goals and Milestones are planning lenses that point into both. Feedback never touches the roadmap directly — intents are the only bridge.

4Relationships (the join tables)

Everything connecting the axes is many-to-many. In the prototype these were ID arrays stored on one side; in the database each becomes a join table. Two of them carry payload — that's why they exist as first-class tables rather than plain pairs:

LinkCardinalityPayload on the link
Goal ↔ Feature / Slice / Capabilityn : m—
Goal ↔ Intentn : m—
Feature ↔ Intent, Slice ↔ Intentn : m—
Milestone ↔ Goaln : m—
Milestone ↔ structure object (milestone_scope_links)n : m, polymorphic over 5 kindsMoSCoW priority + note — the same feature can be must in one milestone and could in another

5Design decisions worth defending in a review

  1. Arrays → join tables. The prototype stores links as ID arrays on the container and scans for reverse lookups. Join tables give both directions, referential integrity, and indexes.
  2. MoSCoW lives on the milestone↔object link, not on the object. The prototype's most important rule: priority is per milestone, deliberately non-cascading to children.
  3. Milestone versioning = self-reference + family key. Cloning (from any version, snapshots included) creates the next version in the same version_family_id; the current head gets locked_at stamped. Exactly one unlocked, editable head per family — enforced by a unique index. Deleting the head hands editability back to the previous version.
  4. Audit log is append-only and denormalized. Entries store object labels and old/new values as text, and are anchored to the version family — so history survives deletion of the objects it mentions and even of the milestone version itself.
  5. Unassigned features are area_id NULL (prototype used an empty string) — supports the "type a feature name on a goal card, organize it later" flow.
  6. Signals stay out of the roadmap schema. The only doorway is wip_items of type intent; link tables enforce that with a composite foreign key on (id, type).

6Proposed rules — how they map onto this model

A target rule set was proposed for this domain (DeliveryWeek → Goals → Intents → Tasks, a strict product hierarchy, slice-level capability selection). Most of it is already how this model works. Below: what matches as-is, where the rules and the current model genuinely differ, and the decisions the rules force before the schema can adopt them.

Already matching no change needed

Goal ↔ Intent and Signal ↔ Intent are many-to-manyExactly the current link tables — goals link intents, never own them.
Area → Feature Set → Feature → Capabilities + SlicesThe structure tree is identical, including capabilities and slices as the two breakdowns of a feature.
"Releases package scope; they do not define hierarchy"Milestones here own nothing — they are pure pointer collections over goals and product objects.
"Signals do not generate work automatically"Built-in philosophy: finishing work never auto-resolves feedback without a human review step.
The Auth worked example"Auth → Registration → Register with email → 5 capabilities → beta slice" is literally this model's own seed example, so the vocabulary maps one-to-one.

Real differences rules ≠ current model

1 · DeliveryWeek is an entity in the rules; today it's just a date.

Currently a goal carries a week_start date and "a week" is an implicit bucket of goals sharing that date. The rules make DeliveryWeek first-class (e.g. DW-24) with goals pointing at it. Same meaning, cleaner structure — an easy, low-risk upgrade.

2 · "Every Feature belongs to one FeatureGroup" is stricter than the current flow.

Today the Feature Set layer is optional, and features can exist fully unassigned — by design: you can type a new feature name straight onto a goal card and organize it into the hierarchy later. The latest prototype iteration loosened this further (capabilities and slices can now be captured before their parent feature is known, flagged "needs mapping"). The rules and this capture-now-map-later workflow can coexist only if the rule is treated as the end-state invariant — everything must be mapped eventually — rather than a hard constraint at creation time. That's a product decision, not a schema detail.

3 · Slice ↔ Capability selection — and the open question of where MoSCoW lives.

The rules make the slice-capability table first-class (included / excluded / deferred, plus must / should / could / wont). The current model deliberately dropped it: the prototype removed that table from the UI in V1 and moved MoSCoW priorities to the milestone scope links instead (so the same feature can be a must in one release and a could in another). The rules put the weights back at the slice level and say nothing about release-level priorities. These are two different planning philosophies — per-slice scope vs. per-release scope — and the schema needs a decision: one of them, or both.

4 · "Every Task belongs to one Intent" is a real hierarchy the current model only approximates.

There is no parent column today — "tasks of an intent" are inferred from follow-up references, and tasks can be standalone or created directly from a signal. The rules make parentage mandatory and (by listing only Signal ↔ Intent) imply signals stop linking to tasks directly. Adopting this means adding a required parent and retiring the standalone-task and task-from-signal flows.

5 · "Every active Intent must satisfy at least one Goal" — not enforced anywhere yet.

Intents are routinely born goal-less today (from signals, or as planning drafts in a group workspace). Conveniently, the newest prototype changes add an isDraft flag on intents — which provides exactly the active/inactive distinction this rule needs: a draft may be goal-less, and finalizing it would require at least one goal link. Enforcement would live in the app layer.

Decisions the rules force open

ThemesThe rules keep themes as overlay tags ("Auth Readiness"). The current schema doesn't model them — adopting the rules brings them back as two small tables (same link pattern as milestone scope).
Release scope breadthThe rules scope releases to Features / Slices / Capabilities / Goals. The current model also allows linking whole Areas and Feature Sets ("broad planning levels"). Keep or cut?
Rule 12"Future goals link broad, near-term goals link concrete" is a process rule — the link mechanism already supports both granularities; the time-horizon discipline would be app-level validation or convention, not schema.
Versioning & auditMilestone version families and the append-only audit log aren't mentioned in the rules and conflict with nothing — they survive by default unless explicitly dropped.
